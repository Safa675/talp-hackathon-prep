# Kestrel persona simulation: Gemini 3.7 Flash request design

**24 October 2026.** This design uses the 24 fixed prototypes in `personas_prototype.jsonl` and the TALP challenge contract. It is a request and data specification, not a completed simulation.

## Recommendation

Use **one model call per persona per week**, plus one call per persona for each required start/end probe in `plan_1` and `nodecision_1`. That is `24 × 10 × 5 = 1,200` weekly calls and `24 × 2 × 2 = 96` probe calls, for **1,296 calls** in the five required runs. Calls for different personas in the same week may run concurrently. Weeks for the same persona must run in sequence because their state changes. Keep the model's choice of what the persona says and does in its response. Code may calculate flight exposure, available recovery capacity, cost, and metrics from those responses.

Google lists a **1,048,576-token context window** and **65,536 maximum output tokens** for `gemini-3.7-flash`. These are ceilings, not sensible prompt sizes. For this task, aim for **1,200–2,000 input tokens and 150–350 visible output tokens per weekly call**; allow about **2,500 input tokens** on a complex crisis week. These figures are **design targets**, not measured usage. Use the model's `count_tokens` method on the exact assembled request and `usage_metadata` on responses to record actual counts. A 1,500-input/250-visible-output design would send roughly 1.94 million input tokens and produce 324,000 visible output tokens across 1,296 calls, before internal thinking tokens and retries. Thinking can add latency and billed output tokens. [Google model page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-7-flash), [Google Gen AI SDK](https://googleapis.github.io/python-genai/).

## 1. Persona record: fixed, short, behaviorally useful

Keep each persona at approximately **100–220 tokens**. The existing prototype file is roughly 460 bytes per record on average and is a suitable starting shape. `group` must match a Kestrel dossier group. Include a short `context` sentence only when it adds a constraint not already encoded.

```json
{
  "id": "K06",
  "group": "families visiting relatives",
  "name": "Renee",
  "age": 38,
  "trip_week": 8,
  "route": "Philadelphia to Orlando",
  "party_size": 4,
  "date_flexibility": "none",
  "checked_bags": 2,
  "budget_buffer": "low",
  "booking_channel": "website",
  "contact_channel": "text",
  "alternative_airline": "hard to find four seats",
  "priority": "get all four people to a reunion together",
  "context": "Traveling with two children; a split-flight offer is unacceptable."
}
```

**Fixed fields:** group, trip purpose, route, booked travel week, party/group size, baggage, booking/contact channel, flexibility, budget buffer, alternative options, assistance need if relevant, priority, one defining prior experience. Name and age are useful for live questioning but should not drive behavior by themselves. Avoid redundant personality adjectives, invented loyalty tiers, irrelevant lifestyle details, and copying the whole dossier into every persona.

**Dynamic fields live outside `personas.jsonl`:** current itinerary and confirmation status, whether the person has learned of the crisis, last support contact, trust/rebook intent, an unresolved promise, and a short memory. Never overwrite the fixed persona file between runs.

## 2. World state: generated by the simulation, supplied as facts

For each persona-week, assemble a compact **observed-world** block, normally **150–350 tokens**:

- week/date and whether this persona has a booked flight this week;
- route/base exposure, whether baggage or assistance service is affected, and specific delay/cancellation information known to the passenger;
- rebooking, partner-seat, refund, hotel, and support options actually available;
- the exact crisis announcement only if this persona encountered it;
- the exact decision message only from its effective week onward and only for its target;
- normal Kestrel policy facts that matter now (for example, mandatory DOT refund eligibility or standard voucher rules).

World facts must be internally consistent. The world model can decide that the strike reduces capacity, but it must not choose the passenger's action. The prompt must not leak future surprise events or future company decisions. The exact decision message must be preserved **word for word** in `calls.jsonl` prompts, per the challenge checker.

## 3. Memory: a rolling state, not ten weeks of chat history

Carry **80–150 tokens** per persona: one or two sentences on what happened, the latest booking state, last support outcome, any remaining obligation, and current willingness to book again. Update it from the model's response and world events. Save the full request and full response to `calls.jsonl`, but do not resend all earlier transcripts. If a fact affects a later choice, preserve it in the rolling memory or structured state. For example:

> Week 7: Received a strike warning and kept the booking. Has not contacted support. Needs all four seats before Dec 23. Trust is cautious after a prior late notice. No refund or reroute has been accepted.

Keep the previous **one** action/response as a compact state summary. More history usually repeats facts and makes the model overreact to old events.

## 4. Weekly API request

Send a **single persona per request**. Do not put all 24 personas in one prompt: separate calls preserve individual state, make outputs traceable to `calls.jsonl`, and allow concurrent processing. Use an English prompt because the dossier's required status strings and decision messages are English. The persona can still have a natural voice.

**System instruction** (about 120–180 tokens):

> You are simulating one Kestrel Air customer, using only the supplied persona, current state, and information this customer has actually received. Decide what this person says and does this week. Stay consistent with their constraints, but allow attitudes to change after events. Do not assume future events or create airline policies, flights, compensation, or available seats. Safety and legally required refunds are fixed. If an offered option is unavailable, do not choose it. Give a concise reason in the customer's voice. Report one exact Kestrel status and whether they would book Kestrel again. For a travel-agency persona, speak as the group coordinator and describe the group's dominant outcome.

**User content**: separate compact sections such as `PERSONA`, `CURRENT_STATE`, `THIS_WEEK`, `OPTIONS`, `EXACT_COMPANY_MESSAGE`, `TASK`. The company message should be copied verbatim, without a paraphrase. Do not include external Pegasus/Frontier/Allegiant research in the weekly request; that research guided persona construction and is not a fact a Kestrel passenger sees.

**Illustrative week-8 user content** (the flight and seat availability here are example world inputs, not claims from the dossier):

```text
PERSONA: {the single K06 JSON record}
CURRENT_STATE: Booking for four, Philadelphia–Orlando on Dec 22. No prior change. Last week Renee heard that ground handling workers might strike; she has not contacted support.
THIS_WEEK: The strike began. Kestrel canceled this booking at 08:10 and texted Renee at 08:20. Two checked bags are included in her original booking. She has children in the party.
OPTIONS KNOWN TO RENEE: A Kestrel flight on Dec 24 has four confirmed seats together; refund is available if she declines. No partner flight with four seats has been offered. Airport phone queue estimate is 45 minutes. She can check the app now.
EXACT_COMPANY_MESSAGE: [insert the applicable locked decision message verbatim, or omit this section if none applies]
TASK: Decide what Renee says and does now. Use only these known options. Report her travel status and whether she would book Kestrel again. Keep the reason brief.
```

**Suggested response fields:**

```json
{
  "status": "rebooked",
  "would_book_again": "maybe",
  "action": "Accept the confirmed Dec 24 flight and ask whether the four seats stay together.",
  "said": "I need one confirmed plan for all of us.",
  "reason": "Four seats on a rival flight are unaffordable and a later family gathering still works.",
  "support_contact": "app",
  "complaint": false,
  "memory_update": "Accepted Dec 24 reroute for four; awaiting seat confirmation; trust fell after slow notice."
}
```

The allowed `status` enum is exactly `flies as planned`, `rebooked`, `moved to another airline`, `canceled the trip`; `would_book_again` is `yes`, `maybe`, or `no`. The status words must appear in the raw model response so `weekly.jsonl` can cite that call. The model should give the action and reason; code should validate values and retry a malformed response with the same facts rather than fabricate a new status.

**Week without a flight:** the challenge still requires one allowed status for every persona every week. Add `had_flight_this_week: false` in `weekly.jsonl` and explicitly define a convention for the forced `status` value in `TEAM_DOC.md`; exclude those rows from travel and 24-hour resolution denominators. The dossier's wording does not supply a semantically clean “no trip” status, so disclose this as a measurement limitation to the board.

## 5. Model settings and Python skeleton

For `gemini-3.7-flash`, Google currently documents `thinking_level` values **LOW, MEDIUM, HIGH**; MEDIUM is the default. `MINIMAL` is unsupported. Use **LOW** for ordinary weekly choices and **MEDIUM** for the strike/crisis weeks or a decision with several competing recovery options. Google's 3.7 developer guide says to omit `thinking_budget`, `temperature`, `top_p`, `top_k`, `candidate_count`, and penalty fields. The TALP handout's older `thinking_budget=0` suggestion should therefore not be copied into a 3.7 request. Its “temperature above 0” intent is met by the documented default temperature of **1.0**; Google says explicitly setting that parameter is ignored by this model. Record this model-specific choice in `TEAM_DOC.md`. [Google 3.7 guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/guides/gemini-3-7-flash), [model page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-7-flash).

```python
import json
import os
from google import genai
from google.genai import types

MODEL = "gemini-3.7-flash"
client = genai.Client(vertexai=True, api_key=os.environ["TALP_KEY"])

STATUS_SCHEMA = {
    "type": "OBJECT",
    "properties": {
        "status": {"type": "STRING", "enum": [
            "flies as planned", "rebooked", "moved to another airline", "canceled the trip"
        ]},
        "would_book_again": {"type": "STRING", "enum": ["yes", "maybe", "no"]},
        "action": {"type": "STRING"},
        "said": {"type": "STRING"},
        "reason": {"type": "STRING"},
        "support_contact": {"type": "STRING"},
        "complaint": {"type": "BOOLEAN"},
        "memory_update": {"type": "STRING"},
    },
    "required": ["status", "would_book_again", "action", "said", "reason", "memory_update"],
}

def generate_week(system_text: str, user_text: str, run_seed: int, crisis_week: bool):
    response = client.models.generate_content(
        model=MODEL,
        contents=user_text,
        config=types.GenerateContentConfig(
            system_instruction=system_text,
            seed=run_seed,
            thinking_config=types.ThinkingConfig(
                thinking_level="MEDIUM" if crisis_week else "LOW"
            ),
            response_mime_type="application/json",
            response_schema=STATUS_SCHEMA,
            max_output_tokens=1024,
        ),
    )
    result = json.loads(response.text)
    # Save user_text + system_text as the full prompt, response.text as the full response.
    # Save response.usage_metadata and model version separately for cost/diagnostics.
    return result, response
```

`seed` is a best-effort reproducibility control, not a guarantee of identical outputs. Use the **same seed for `plan_1` and `nodecision_1`**, another shared seed for `plan_2` and `nodecision_2`, and the first seed for `plan_nosurprises`. Keep persona records identical. The checker tests different **answers** between the two plan seeds and between the two no-decision seeds, not just different seed numbers. A structured output schema is supported by 3.7. Keep schema small because its constraints may consume context and affect output. [Google inference reference](https://docs.cloud.google.com/gemini-enterprise-agent-platform/reference/models/inference), [structured output](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/capabilities/control-generated-output).

The hackathon key uses the Vertex-style global endpoint without a project or location, as specified in the challenge. Do not log the key. The public Gemini Developer API page and Google Cloud model page currently describe different lifecycle states for the 3.7 model ID; rely on the **actual endpoint response** and record the returned model version in run metadata. [TALP challenge](yeni-case-5-sirket/02-challenge.md), [Google Cloud 3.7 page](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-7-flash), [Gemini Developer API notice](https://ai.google.dev/gemini-api/docs/generate-content/whats-new-gemini-3.7).

## 6. Exact input budget per weekly call

| Section | Target tokens | What belongs there |
|---|---:|---|
| System instruction | 120–180 | Persona role, bounds, response behavior |
| Kestrel facts relevant this week | 120–220 | Only applicable service rules and current policy |
| Fixed persona | 100–220 | One JSON record, not all 24 |
| Rolling state/memory | 80–150 | Prior response condensed plus booking state |
| Current week and available options | 150–350 | Exposure, announcements, real options |
| Exact decision message | 0–200 | Only if active and targeted; preserve all words |
| Task and output request | 80–150 | What decision to make now |
| **Typical total** | **650–1,470** | Leave room for special crises, up to ~2,500 |

The token table is an initial engineering budget. Count actual tokens after assembling the exact request. The one-million-token ceiling does not improve the persona by itself; repeated dossier text, other personas, past transcripts, and irrelevant public research can dilute the current decision and multiply the cost across 1,296 calls.

## 7. Probe calls

At week 0 and week 11, ask all eight required questions in **one call per persona** for `plan_1` and `nodecision_1`. Use the exact wording from the challenge. Respond with eight integer scores keyed `1a` through `4b`; do not reverse-score `2b` or `4b` in the raw `probe.jsonl`. Week 11 receives the persona's final rolling memory; week 0 receives the fixed persona and pre-simulation state. Log both full prompts/responses and link each answer to its call ID.
